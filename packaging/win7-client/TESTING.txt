Horizon Direct3D9 preview - Windows 7 SP1 x64

Requires prepared legal Horizon resources for Minecraft 26.3, the manufacturer's
GPU driver, and an N455-compatible x64 CPU (SSE3/SSSE3). No Java or shader compiler
is needed during play. GMA3150 smoke passed according to the owner; the full game
on GMA3150/HD4570 remains unverified. This update merges fork main 298c01b0206d.
The previous RTX3050 build reached 580+ FPS at 16 chunks, but only 80 at 48 chunks.
This update needs a repeat of that comparison; no new FPS/RAM result is claimed.

Launch:
1. Extract this ZIP once; horizon-client.exe is directly inside. Select that EXE
   as the native client in your launcher. DX9 is the default in this executable.
2. For diagnostics, close the game and launch it with --control. This is an
   argument to horizon-client.exe, not to the launcher or horizon-ctl.exe.
   Example in PowerShell, from the extracted folder (replace both paths):
   .\horizon-client.exe --control --resources "C:\path\to\26.3" --game-dir "C:\path\to\test-game"
   If your launcher has a game-arguments field, append --control there instead.
   Use a COPY of a save. No low graphics preset is installed.

Short retest:
Use the same save/view/settings at 16 and 48 chunks; wait for loading to settle.
Compare HUD on/off (F1), F3 axes, F5 skin depth, inventory/chat and fog. Try F3+A,
turn around, resize, Alt+Tab, fullscreen, then save/reopen. F2 saves screenshots.
Send latest.log and build-info.txt with any problem. Texture filtering uses the
existing setting; None keeps nearest mip transitions, nonzero uses supported
linear/trilinear filtering. Graphics settings are never rewritten.

Optional reports, from a SECOND PowerShell in this extracted folder while the
world runs. Start the GAME with --control as above, otherwise these commands
return a connection error. If the launcher sets HORIZON_HOME, use that same home
in this terminal:
  .\horizon-ctl.exe bench 20 > frame-stats.json
  .\horizon-ctl.exe memory > memory.json

New upstream profiler, useful for a 48-chunk capture and F3+A/camera movement:
  .\horizon-ctl.exe profile client start --seconds 20 --timeline --no-samples
  .\horizon-ctl.exe profile client status
  .\horizon-ctl.exe profile client stop
The capture stops automatically after 20 seconds; stop/status reports its path.
Send that .hzperf file if needed. This records frames, memory and CPU timeline
phases, including the DX9 section worker. Windows CPU stack/heap sampling and
DX9 GPU timestamps are unavailable. No capture is uploaded automatically.
The older trace command also writes .hzperf now, not browser-trace JSON.

What changed:
- Dense shared column storage and cheap presence keys for empty sections.
- Exact reuse of unchanged solid draw plans and visibility indices.
- Hardware-only VS2: exact 20/28-byte vertices and smaller CPU shadows; arbitrary
  model precision falls back safely. GMA/software vertex processing keeps FFP
  and 32-byte vertices; no hardware VS2 requirement has been added.
- Initial section conversion/encoding on one CPU worker shared with compaction.
  A conservative 8 MiB charge bounds queued inputs/results; edits and overflow
  stay synchronous. COM uploads stay on the render thread. This is a queue
  bound, not an 8 MiB cap on all worker scratch or the terrain GPU cache.
- Prepared animation mip/extrusion pixels cached up to 4 MiB payload.
- F3 axis crosshair rendering from the existing CPU frame.

The five-second log reports CPU elapsed phases (including driver waits), draws,
binds, uploads, requested/live terrain storage, compressed CPU shadows, GUI
locks, compact20/wide28/ffp32 bytes, staging queue/conversion times, animation
cache hits/misses, solid_plan_reused and uncached_visible_bytes. Requested GPU
storage is not measured physical VRAM. Other backends' GPU timestamps cannot
be compared directly with DX9 CPU phase times.

Automatic terrain-cache targets use driver/system-memory hints up to 2 GiB;
there is no fixed 128 MiB cap. Remove old overrides for the ordinary test:
HORIZON_D3D9_MESH_MIB / HORIZON_D3D9_TEXTURE_MIB. These remain optional diagnostic
overrides. Allocation pressure falls back to drawable CPU shadows/streaming,
not a fatal budget error. User render distance and quality remain unchanged.

Limitations: SDR, simplified End portal, no fancy clouds/star field, enchantment
foil, shader packs, PBR, post effects, LOD, GPU occlusion/skinning, frame generation
or split-screen compositor. Base terrain/models, entities/hand, menus/HUD/chat,
weather and overlays remain. The Win7 ZIP currently contains DX9 only; a single
EXE with lazy modern-API imports is a separate unresolved integration task.

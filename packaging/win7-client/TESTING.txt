Horizon DX9 - Windows 7 SP1 - x64/x86 Thin LTO distribution

Extract this ZIP once: horizon-client.exe is directly inside. Select it as your
launcher's native client. Supply your own legal prepared Minecraft 26.3 resources.
No game assets, Java, shader compiler or external control tool are included.

Requirements: D3D9 HAL driver, Win7 SP1; x64 SSE3/SSSE3 or x86 SSE3. x86 is
large-address-aware. Subsystem/API target stays Win7. XP + OneCoreAPI is an
owner experiment with known input/long-session issues, not native XP support.

Default initial window: 854x480. Explicit --width/--height/fullscreen wins.
Graphics > General > Direct3D 9 offers Auto/Hardware/Software VP and 16/32-bit
color; these require restart. Software VP transforms on the CPU and rasterizes
on the GPU. GMA3150 uses it automatically. RGB565 is preferred with 32-bit fallback;
D24 depth takes priority. Exclusive fullscreen is not required. No fixed 128 MiB
cap, forced low preset or render-distance/FPS reduction is installed.

This integration updates Horizon, enables Thin LTO (opt=3, one codegen unit,
panic=abort), restores enchantment shimmer and keeps ordinary logs quiet. Check:
- Enchanted held/dropped items, inventory/hotbar icons, GUI models and armour.
  Shimmer should scroll, obey masks/depth, disappear at Glint Strength zero and
  follow Glint Speed. Ordinary items should have no extra pass. Custom CIT glint
  remains unsupported. Two-stage adapters approximate glint filtering.
- Immediate breaking/placement, ice/water, F5 skin, depth and GUI transitions.
- Resolution Scale 100/75/50: only the world changes resolution; HUD stays sharp.
  Return to 100 for performance comparisons. Check resize/minimize/restore.
- Mipmap Levels 0/2/4, including changes while Animated Textures is Off. Native
  anisotropy follows driver caps; RGSS is still approximated by linear filtering.
- CPU entity/particle culling Off/Sync/Async. Unsupported API effects stay disabled
  with a reason, preserving saved values. New upstream interfaces must not silently
  enable unsupported GPU pipelines or import newer mandatory Windows APIs.

For TZ3 use the same hardware, route, world state, window, distance, warmup and
saved settings. The source baseline is 9ef29e6bba219e1805f5be1d6636b67a0cfce0c6;
42f0b42d47 captures belong to an older integration. Record EXE/package hashes and
build-info.txt. Repeat the standing scene and fixed server route independently.
A different scene or a successful CPU test does not establish hardware FPS parity.

Profile through game chat, with no --control or other launcher argument:
  /profiler start client
Perform the fixed route for 60-90 seconds, then:
  /profiler stop client
Send the local .hzperf and latest.log. No upload occurs unless you choose it.
Use no gpu/gpu_detail suffix: DX9 has no GPU pass timestamps. Detailed timeline
can stop at its configured cap; ordinary longer phase/health captures still help.
Phases include driver waits. Process CPU/RSS use upstream Windows probes.
Dev packages (build-info.txt: dev_diagnostics=1) log DX9 stats by default, including
5-second per-pass submission totals. HORIZON_D3D9_LOG_STATS=0 disables diagnostics
when explicitly needed. Keep diagnostics on for the current entity experiment;
the first diagnostic-overhead pair has already been collected.
Ordinary packages keep periodic logs off; HORIZON_D3D9_LOG_STATS=1 enables their
existing coarse stats. GPU timings are not instrumented by the P0a counters.

Current dx9-dev experiment: software-VP dynamic entity base geometry uses one
bounded VB upload per early/late phase, followed by the original ordered draws.
It starts in B_staged. With the game focused, press Ctrl+Shift+F12 once to switch
to A_baseline; press again to return to B_staged. No restart, environment variable
or settings change is needed. The log records each switch and closes the previous
native counter window first. Profiles also contain d3d9_entity_mode_A_baseline or
d3d9_entity_mode_B_staged. Hardware VP stays on the original path.

Warm up, record the fixed walk in B, switch to A, return to the same starting
point, and record the same walk again. Prefer B-A-A-B if practical; keep diagnostics
enabled throughout. Start/stop a separate chat profile for each route so whole-run
FPS remains comparable. Standing is a useful regression check but has almost no
entities. Keep all graphics settings and the window unchanged. Send these profiles
and the one latest.log; preserve it before the next application launch.

Expected invariant: dynamic DIP count, triangle count, sum NumVertices and VB
payload bytes stay comparable at matching route locations. Base-geometry VB locks
should fall; glint, world primitives, oversized groups and static entities retain
their own uploads. Extra consolidation copies can cost more than the locks saved.
Check skins, held/dropped items, armour/glint, alpha/depth, resource/world changes,
resize and minimize/restore in both modes. A measured GMA gain is still pending.

No new hardware FPS claim is made by this package. Shared generation/gameplay
optimization is not the renderer task. See docs/legacy-d3d9.md in the repository
for architecture and docs/legacy-d3d9-perf.md for the P0a scope and TZ3 handoff.
